# Data Structures

On the server side, the central data structure is the road graph, implemented by the `Graph` type. It combines the static road network with the extra indexing needed for fast hierarchical routing. In practice, this structure stores the full list of `Nodes`, the full list of directed `Edges`, a compact adjacency representation for the base road graph, the partition `Cells`, and a second adjacency structure for the overlay graph. This gives the routing engine one object that contains both the physical road network and the preprocessed hierarchy built on top of it.

The base graph itself is represented in a compact, array-oriented form. A `Node` stores the original map identifier, geographic coordinates, projected planar coordinates, and the cell to which the node belongs. An `Edge` stores the source node, destination node, travel-time weight, physical distance, nominal speed, road class, and direction flags. Instead of keeping a pointer-based adjacency list for every node, the server uses CSR-style arrays: `AdjacencyList.Offsets` marks where each node's outgoing edges begin, and `AdjacencyList.EdgeIDs` stores the edge identifiers consecutively. This is a good fit for shortest-path search because it is memory-efficient, cache-friendly, and fast to scan sequentially.

The graph preprocessing stage adds a second level of structure around this base graph. The partitioning step divides the network into `Cell` objects, and each cell stores its boundary nodes in `BoundaryNodeIdxs`. The graph also keeps two boundary lookup arrays: `BoundaryBaseIdxs`, which translates boundary-node indices back to base-graph node indices, and `BoundaryNodeIdx`, which performs the reverse lookup. On top of that, the server builds an `OverlayAdjList`, which is another CSR-style adjacency list, but only over boundary nodes. Its `OverlayEdge` records are of two kinds: cross-cell edges that connect neighboring cells directly, and shortcut edges that summarize the best internal path between two boundary nodes in the same cell. This overlay is the key data structure behind the hierarchical router. During preprocessing, the partitioning code also uses a temporary `FlowNet` residual graph to run the inertial-flow bisection step that creates the cells.

These graph structures are reflected directly in the routing algorithms. A route search is not represented as one large monolithic state object; instead, the code uses a few small, purpose-built structures. The search frontier is maintained with a typed binary min-heap (`Heap[T]`), used by both Dijkstra and A*. Distances and predecessor relations are kept in sparse maps such as `map[uint32]float32` for tentative costs, `predEntry` for base-graph predecessors, and `overlayPredEntry` for overlay predecessors. The hierarchical query then becomes a sequence of searches over different structures: Dijkstra inside the source cell, A* over the overlay graph, and multi-source Dijkstra inside the destination cell. The final result is materialized as a `Route`, which is a slice of `Step` records containing the ordered nodes, incoming edge IDs, cumulative distance, and cumulative travel time.

Besides the graph itself, the most important runtime structure is the live traffic store. The `Store` type maintains per-edge traffic state in dense arrays indexed by `EdgeID`. It stores the current weight multiplier and density using atomic values, and it also keeps auxiliary edge lists such as `dirtyEdges`, `pendingEdges`, and `activityEdges`. This design is important in practice: instead of recomputing all overlay shortcuts after every observation, the server tracks only the edges whose traffic state changed and customizes only the affected overlay weights. In other words, the dynamic part of the system is also organized around compact edge-indexed arrays and change lists, not around expensive global recomputation.

Two smaller supporting structures are worth mentioning because they connect the algorithms to the rest of the system. First, nearest-node lookup is handled by `SnapIndex`, which uses a fixed spatial grid whose buckets store node indices, allowing route requests to be snapped to the graph quickly without scanning all nodes. Second, active navigation is tracked through session-oriented structures: each `Session` stores the current route, the current step index, and live navigation metadata, while the session `Manager` maintains a `sessions` map and a reverse `edgeSubscribers` map from road edges to the sessions affected by them. This is what allows graph-level events such as congestion on a specific edge to propagate efficiently to the relevant routes.

Overall, the project relies much more on compact arrays, index mappings, and sparse search state than on large object hierarchies. That choice matches the problem well: routing and traffic propagation are dominated by repeated graph traversal, so the implementation favors data structures that support fast iteration over outgoing edges, efficient boundary-node access, and localized updates to dynamic weights.
